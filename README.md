# Savour Partner

A mobile-first merchant workspace and a small shared customer marketplace built on the repository's actual Next.js App Router, PostgreSQL and Drizzle starter.

## Repository audit

The supplied repository began as a Merchant-only Next.js/PostgreSQL foundation rather than the described Vite/Express/POS application. Merchant now pairs with the separate Marketplace through an authenticated, business-scoped integration API; it does not share the Marketplace database URL or duplicate its order lifecycle. Marketplace and the connected POS remain authoritative for paired business orders.

## Supabase setup

The app uses Supabase as managed PostgreSQL through the server-side `pg` driver. It does not use Supabase Auth or the browser Data API: app accounts and sessions are managed by the app. Keep the Supabase database password and connection URL private; only set `DATABASE_URL` in the Vercel project's server environment variables. For Vercel, use Supabase's transaction pooler connection string and its required SSL parameters. Never expose a database URL, password, or service-role key to browser code.

Install the Supabase CLI, authenticate with `npx supabase login`, then link the local project with `npx supabase link --project-ref <project-ref>`. Set the database password when the CLI prompts for it; do not put it in source control or chat. Apply schema migrations to the new, empty Supabase database with `npx supabase db push`. The ordered, deployed migrations are in `supabase/migrations/`; the matching `drizzle/` files are used by local development and CI and must be kept in sync with them. Tables have row-level security enabled and no Data API policies, and direct `anon`/`authenticated` table access is revoked. The server connects with its private database URL.

For local development, set `DATABASE_URL` to a Supabase PostgreSQL connection string before `npm run dev`. No demo records are inserted into the database. Signed-out visitors see a clearly labeled, non-persistent sample workspace; real accounts use only server data.

For service-to-service approval, configure a long random `MARKETPLACE_ADMIN_TOKEN` on the server and call `POST /api/admin/approval` with `Authorization: Bearer <token>` and `{ "businessId": "...", "status": "approved" | "rejected" }`. Only pending businesses can be reviewed. Approval never opens the store automatically. The same token protects `POST /api/admin/owner` with `{ "businessId": "...", "email": "owner@example.com" }`, a recovery hook for an outlet created under the wrong account. The destination account must already exist and may own other outlets; the old account is left unchanged and every decision is audit logged. These are minimal server-to-service hooks, not an administrative review UI or a regulatory verification system.

## API surface

- `GET/POST /api/auth`: account registration, login, logout and session lookup. Passwords use salted scrypt; sessions are opaque, hashed in PostgreSQL and held in an HttpOnly SameSite cookie.
- `GET/POST/PATCH /api/merchant/business`: draft, details, hours and availability (settings permission: owner or manager). Opening requires approval. `POST` with `{ "type": "...", "createNew": true }` creates another outlet for the signed-in owner and makes it active in this session; without `createNew` it resumes the existing draft so setup cannot create duplicates.
- `GET/POST /api/merchant/active-business`: list the outlets the caller owns or staffs (with the role for each), and switch the active outlet for this browser session. Switching is validated server-side; ordinary requests never trust a client-supplied business id.
- `GET/POST/PATCH/DELETE /api/merchant/menu`: menu creation, editing, availability and archival (write permission: owner or manager; servers can set item availability through the dedicated `menu.availability` permission checked by the availability action).
- `GET/POST/PATCH/DELETE /api/merchant/offers`: promotion library (read for manager/owner, write for manager/owner). Create percentage or flat discounts with a code, title, minimum order, optional cap, schedule and usage limit; toggle, edit or archive them. Each row includes redemptions, discount given and influenced order value. Paired businesses proxy these operations to Marketplace instead of writing locally.
- `GET/POST/PATCH/DELETE /api/merchant/staff`: owner-only staff access management. Invite an existing Savour account by email as manager, kitchen or server; change roles, remove access (soft delete) and re-invite (reactivates the same membership). Staff are local to the business: paired listings do not proxy staff access to Marketplace.
- `GET/PATCH /api/merchant/orders`: paginated, filterable order history (read for all staff roles) and expected-status transitions (write for manager/kitchen/server). A transaction records each successful change; conflicting updates return 409. Ready is distinct from completion. Pickup orders complete directly from ready. Delivery orders move ready → out for delivery → completed, so the rider handoff can be advanced (and simulated) from the merchant workspace when no courier integration is connected. Active orders also accept a fulfilment-only update (pickup ↔ delivery) that checks the business fulfilment settings, requires a delivery address, persists the change, and records it in the order event history.
- `GET/POST /api/marketplace/feedback`: token-scoped customer rating (1–5) and optional review on a completed first-party order. One immutable review per order; the order token is the only credential. Merchant tracking reads the feedback and any reply with the same token.
- `PATCH /api/merchant/feedback`: one immutable owner reply to a customer review, recorded in the order event history. Paired businesses proxy the reply to Marketplace instead of writing locally.
- `GET /api/merchant/overview`: server-derived counts, today's completed gross order value, authoritative net settlement records mirrored from Marketplace and a 30-day feedback summary (average rating, review count, bad orders ≤ 2★, pending replies). `feedback.available` is false when a connected Marketplace does not publish those metrics.
- `POST /api/merchant/settlements/sync`: force an idempotent pull of the signed-in business's Marketplace settlement feed; safe to retry.
- `GET /api/merchant/exports?type=revenue|settlements[&from&to]`: downloadable UTF-8 CSV statements using the same range and `settlements.read` permission as the Earnings screens. Revenue mirrors the authoritative paired total in one summary row; settlements list the locally mirrored payout history (up to 5,000 rows). Formula-like cells are neutralised.
- `PATCH /api/merchant/business` with `{ action: "closure" }` or `{ action: "leaves" }`: temporary closure overlays (with an absolute reopening time that expires without a cron) and planned leave days on Asia/Kolkata dates. Paired listings send the overlay to Marketplace, which enforces it for discovery and checkout; existing orders are never cancelled.
- `GET/POST/DELETE /api/merchant/marketplace-link`: read the current Marketplace pairing (including a live `valid` token check), redeem a one-time pairing code, or disconnect and revoke the remote token.
- `GET/POST /api/marketplace`: approved/open business listings, currently live offers, available items, token-protected customer tracking and idempotent order creation. Prices and discounts are calculated on the server from stored menu prices; store status, hours, item availability, offer schedule, minimum order and usage limits are rechecked in a transaction. Applying a different code with the same idempotency key is rejected. Order creation is refused for paired businesses, which accept orders through Marketplace.
- `POST /api/integration/courier` and `POST /api/integration/payment`: HMAC-signed provider webhooks. Verified events update delivery/payment state idempotently, dedupe by event id and ignore older timestamps; bad signatures are rejected and audit logged. No browser session is used.
- `POST /api/admin/approval`: server-token-protected review hook.
- `POST /api/admin/owner`: server-token-protected recovery hook that moves one outlet to an existing owner account, which may already own other outlets.

- `GET/PATCH /api/merchant/compliance`: advisory compliance snapshot for the active outlet — registration details, KYC/FSSAI/tax status summaries, advisories, agreement state, masked payout mirror and document limits. Owners may edit; managers read only.
- `GET/POST /api/merchant/compliance/documents` and `GET/DELETE /api/merchant/compliance/documents/[id]`: encrypted document vault. Owner-only writes; owners and managers read/download. Uploads are multipart (`kind`, optional `expiresAt`, `file`), checked for MIME/magic-byte/size, encrypted with AES-256-GCM and stored in a private Supabase bucket; browsers only receive bytes proxied through an authenticated route.
- `GET/POST /api/merchant/compliance/agreement`: read the current agreement (version `2026-11-01`) or record an explicit owner acceptance with the version and SHA-256 content hash. Acceptances are append-only, one per outlet/version.
- `GET/POST /api/merchant/compliance/payout`: view authoritative Marketplace payout status or forward raw UPI/bank details to Marketplace. Locally only a masked label, reference, status and sync time are mirrored.
- `GET/POST /api/merchant/compliance/invoices` and `GET /api/merchant/compliance/invoices/[id]/pdf`: list mirrored Marketplace invoices and local pro forma documents, mirror new invoices by date range, create a pro forma document for a completed unpaired order, and download a clearly labelled PDF.

## Outlets (branches)

An outlet is one `businesses` row. Owners may run several outlets, and a staff member may belong to several, with an independent role in each. The active outlet is stored on the browser session (`sessions.active_business_id`), so switching outlets on one device does not affect another; older sessions fall back to the account's first outlet. The outlet switcher appears in the top bar when more than one outlet is available, and Business settings offers **Add outlet**. Every existing operational table is already keyed by `business_id`, so orders, menu, offers, reviews, staff and reports are scoped to the selected outlet automatically. Each outlet has its own Marketplace listing, pairing code and encrypted token; tokens are never shared. There is no brand/organisation table and no cross-outlet rollup in this phase — customers see each branch as a separate Marketplace listing. See `supabase/migrations/20261122000000_multi_outlet.sql` (Drizzle: `drizzle/0015_multi_outlet.sql`).

## Staff roles and permissions

The business owner is implicit from `businesses.owner_id` and has every permission on that outlet. Team members are rows in `staff_members` with one of three roles:

- **Manager:** orders, menu, offers, settings, overview, settlement views and read-only compliance records. Cannot manage staff, write compliance records or change the Marketplace connection.
- **Kitchen:** the order queue only; no menu pricing, offers, feedback, payouts or compliance documents.
- **Server:** orders, item availability and customer feedback replies; no offers, settings, payouts or compliance documents.

`/api/auth` returns the caller's active `business`, its outlet-specific `role`, and a `businesses[]` list of every available outlet with its role and pairing state; the merchant UI hides unavailable navigation and actions. Permissions are enforced server-side in `requireBusiness(permission)` (`src/lib/roles.ts` and `src/lib/server.ts`): every merchant endpoint checks the relevant capability, so hiding a button is never the only guard. Denied actions are audit logged as `staff.permission_denied`. Adding someone requires them to have already registered a Savour account with that email; there is no email invitation or self-signup flow yet.

## Savour Marketplace integration

The Merchant App can be paired with the canonical Savour Marketplace without sharing its PostgreSQL database. In the Marketplace partner console, open **Merchant App** for the listing that represents the outlet, generate a one-time pairing code, then enter it in **Savour Merchant → Business settings → Marketplace connection**. Codes expire after 10 minutes and can be used once. Repeat this per outlet with a fresh code: one Marketplace listing pairs to one Merchant outlet, and each outlet gets its own encrypted token. When a new outlet is added via **Add outlet**, it starts as a local draft and must be paired before it can accept orders. Switching outlets rechecks the new outlet's connection; a stale token on one outlet does not pause polling for the others.

When paired, the Merchant App proxies menu edits, offers, store availability/settings, order inbox, status changes, overview metrics, and net settlement records to the Marketplace APIs using a per-business bearer token encrypted at rest. Marketplace is authoritative for that token and for all paired data: it mints the credential at pairing and keeps only a hash for verification, while the Merchant App holds an encrypted local credential copy solely so it can call the integration APIs between reconnects. The Marketplace database remains authoritative for the published listing, menu, customer orders, payment state, destination bank/UPI accounts and real payouts. The Merchant App does not dual-write Marketplace orders to its own `orders` table; local checkout is blocked for a paired business to prevent duplicate orders. Disconnecting revokes the remote token and then removes the encrypted local copy without deleting order history. If Marketplace cannot be reached or returns a server error, the local link is kept and the request fails so the same connection can be retried; a 401/404 is treated as already revoked. Marketplace stores only a hash of the bearer token, so a locally deleted token cannot be recovered from it: if that ever happens, disconnect the stale link in the Marketplace partner console, generate a fresh one-time code, and pair again.

For customer reviews, Merchant accepts `rating`, `review`, `feedbackAt`, `merchantResponse` and `merchantRespondedAt` on the order payload returned by `GET /api/integration/merchant/orders` (nested under `feedback` or flat; `customerRating`, `customerReview`, `sellerResponse` and `reply` aliases are also read). A merchant reply via `PATCH /api/merchant/feedback` calls `PATCH /api/integration/merchant/orders/feedback` with `{ "orderCode": "...", "response": "..." }` using the same per-business bearer token; Marketplace must own and persist that reply. If the endpoint is missing, the Merchant UI reports the upstream error and refreshes authoritative orders rather than storing a local copy.

For promotions, the Merchant App calls `/api/integration/merchant/offers` (GET, POST, PATCH, DELETE) with the same per-business bearer token. Marketplace owns the canonical offer rows and applies codes at its own checkout; it must accept the same fields as the local offer API (`code`, `title`, `description`, `discountType` of `percent` or `flat`, integer paise `value`, `minOrder`, `maxDiscount`, `startsAt`, `endsAt`, `usageLimit`, `active`) and return `{ "offer": { ..., "id": "..." } }` for writes and `{ "offers": [...] }` for reads. The public customer menu may show `code`, `title`, `description`, `discountType`, `value`, `minOrder`, `maxDiscount`, `startsAt` and `endsAt`; it never exposes usage limits or other businesses' data.

For settlements, Marketplace must expose `GET /api/integration/merchant/settlements` using the same per-business bearer token. Each record represents one completed order and carries `externalId`, `marketplaceOrderId`, `orderNumber`, `grossPaise`, `commissionPaise`, `refundPaise`, signed `adjustmentPaise`, authoritative `netPaise`, `currency`, `status`, `reference`, `paidAt` and `updatedAt`. Merchant validates the feed, reads up to 10 pages of 200 records (2,000 payouts) per manual sync and replaces a row only when Marketplace supplies a newer `updatedAt`; if the feed is longer, the sync is marked `truncated` and the UI says older records remain in Marketplace rather than silently dropping them. Commission and refund are positive deductions; a positive adjustment is a credit and a negative adjustment is a further deduction. `netPaise = grossPaise - commissionPaise - refundPaise + adjustmentPaise`. Marketplace currently has no separate payout ledger, so this feed is projected from its provider-verified payment captures/refunds and each order's platform-fee snapshot; `paidAt` is the capture time, not a bank payout time. Merchant never receives raw account numbers and never initiates a transfer.

Configure `MARKETPLACE_API_URL`, `MERCHANT_APP_INTEGRATION_SECRET`, and `MERCHANT_APP_TOKEN_ENCRYPTION_KEY` using `.env.example`. The integration secret must match on both servers. The encryption key is Merchant-App-only and must be a separate random secret. Real deployments must use an HTTPS Marketplace URL; HTTP is allowed only for loopback hosts (`localhost`, `127.0.0.1`, `::1` and `*.localhost`) so `npm start` can be validated against a local Marketplace on port 3001. Note that Marketplace's own host allowlist rejects raw-IP hosts such as `127.0.0.1` with `400 Bad request`; use `localhost` or a configured hostname there. Run the Merchant App migration that creates `business_marketplace_links` before pairing: `supabase/migrations/20261028000000_marketplace_bridge.sql` (the Drizzle equivalent is `drizzle/0002_marketplace_link.sql`). Do not copy Marketplace's database URL into Merchant; the integration uses authenticated, business-scoped Marketplace integration APIs.

"Marketplace connection is no longer valid" (or the earlier "Marketplace link is missing or expired") is an **upstream 401**, not a Merchant login failure. Every integration read/write sends the per-business bearer token minted at pairing time; Marketplace answers 401 when that token is no longer in `merchant_app_links` — for example after a disconnect/re-pair on the Marketplace side, or when `MARKETPLACE_API_URL` points at a different Marketplace deployment than the one holding the pairing. Merchant deliberately does **not** sign the user out on an upstream 401. Because Marketplace stores only a token hash, the encrypted local copy cannot be repaired: disconnect the stale link (if it still exists), then pair again with a fresh one-time code from the Marketplace partner console. A pairing code is valid for 10 minutes and is single-use. The status endpoint probes Marketplace with the stored token and reports `valid: false` only for a definitive upstream 401; transport or server failures leave validity unknown. The dashboard then shows a “Marketplace connection needs attention” banner and pauses order/menu polling, and Business settings shows “Reconnect needed”, until the link is repaired.

Order reflection for a paired business is a live proxy, not a copy: `GET /api/merchant/orders` and `/api/merchant/overview` read Marketplace's canonical order rows, so a newly placed order appears on the next refresh. Two deliberate exceptions: cash-on-delivery orders appear immediately, while online-payment orders are held out of the merchant inbox until the payment provider confirms `PAID`. Checkout for a paired business through Merchant's bundled customer storefront is refused (409) so it cannot create a local-only duplicate; place customer orders in Marketplace.

## Compliance and money documents

Compliance state belongs to one outlet, not an account or brand, and is **advisory only**: missing or expired items appear as banner-style advisories from `GET /api/merchant/compliance` and never block orders, menu edits or payouts. There is no KYC verification, FSSAI/GST registry lookup, bank/UPI payout setup in Merchant, GST configuration or tax filing. Validation is deliberately narrow — registration-number format, calendar expiry, and file MIME/magic-byte/size — and submission is never presented as verification. Registration details remain free text apart from the GSTIN/PAN/FSSAI format checks.

Access uses the same server-side permission model as the rest of the workspace: `compliance.read` for owners and managers, `compliance.write` for owners only; kitchen and server requests get 403. Every document and invoice route resolves the active outlet from the session, and mutating routes check the origin and are rate limited. Audit entries record detail changes, document uploads/deletes, agreement acceptance and payout/invoice actions without raw identifiers or file bytes.

### Private document storage

Documents are uploaded with a service-role key to a **private** Supabase Storage bucket named `merchant-compliance` (override with `COMPLIANCE_STORAGE_BUCKET`). Set `SUPABASE_URL` (bare HTTPS origin) and `SUPABASE_SERVICE_ROLE_KEY` together in `.env.example`/the deployment; leaving both empty disables uploads and downloads with a 503 and a startup warning, and a half-configured pair fails config validation. Bytes are encrypted with AES-256-GCM under a key derived from `MERCHANT_APP_TOKEN_ENCRYPTION_KEY` with a separate domain label, so the Marketplace token key cannot decrypt documents. The browser never receives the service key, a direct storage URL or the encrypted object: the server creates a 60-second signed URL, proxies the bytes, decrypts them, and returns them with `Content-Disposition: attachment` and `no-store`. Only the document metadata (kind, file name, content type, size, SHA-256, status, expiry, uploader) is kept in PostgreSQL.

### Agreement

The current agreement is version `2026-11-01` with a SHA-256 body hash. An owner accepts it by posting `{ "accepted": true, "version": "2026-11-01", "contentHash": "..." }`; a missing flag is rejected, and a version/hash mismatch returns 409 so the caller must re-read the text. Each acceptance is an append-only row with a unique outlet/version pair, hashed IP and user agent, and is never edited or deleted. A future version needs a fresh acceptance; the advisory reflects the current version only.

### Marketplace endpoint contract (optional)

All calls use the per-outlet bearer token and the same `MARKETPLACE_API_URL` as the other integration APIs. These endpoints are optional: a `404` is treated as "not deployed on this Marketplace" and degrades to the last locally mirrored state with `available: false`; a `401` still invalidates the link normally. Unexpected statuses and malformed payloads fail without changing local compliance state.

- `GET /api/integration/merchant/compliance/payout` returns `{ "payout": { "status", "methodLabel", "reference", "updatedAt" } }`. Status is one of `not_configured`, `pending`, `configured`, `verified` or `action_required`; top-level fields and `label`/`maskedLabel`, `externalId`, `syncedAt`/`createdAt` aliases are also read.
- `POST /api/integration/merchant/compliance/payout` accepts `{ "method": "upi", "upiId": "..." }` or `{ "method": "bank", "accountHolderName": "...", "accountNumber": "...", "ifsc": "..." }` and returns the same shape. Raw account details go **only** to Marketplace; the local row stores `UPI ab***@bank` or `Bank ••••1234 (IFSC)`, plus the Marketplace reference. There is no local payout ledger and no transfer initiated by Merchant.
- `GET /api/integration/merchant/compliance/invoices[?from=YYYY-MM-DD&to=YYYY-MM-DD]` returns `{ "invoices": [...] }` with up to 500 rows. Each row carries `externalId`, `invoiceNumber`, `orderId`, `recipientName`, `recipientGstin`, integer-paise `taxableAmount`/`taxablePaise`, `cgstAmount`/`cgstPaise`, `sgstAmount`/`sgstPaise`, `igstAmount`/`igstPaise`, `totalAmount`/`totalPaise`, `currency`, `status` (`issued`, `proforma`, `cancelled`, `void`), `issuedAt` and `updatedAt`. Sync is idempotent and replaces a mirrored row only when Marketplace supplies a newer `updatedAt`; duplicate invoice numbers in one feed are collapsed. Dates are inclusive `YYYY-MM-DD` calendar days, matching the range convention used by revenue and exports.

### Invoice boundary

Paired outlets only mirror **Marketplace-issued** invoices — Marketplace owns tax configuration, calculation and the original tax invoice. The locally generated PDF is explicitly labelled `MARKETPLACE INVOICE MIRROR` and says it is not the original tax invoice. Unpaired outlets may create `pro forma` documents from completed local orders using the outlet's configured tax inclusivity/rate; these are labelled `PRO FORMA INVOICE`, are not GST tax invoices and are not proof of payment. Paired outlets cannot create pro forma documents, and unpaired outlets cannot sync a Marketplace feed. Listing, filtering and PDF download require `compliance.read`; syncing and pro forma creation require `compliance.write`. See `supabase/migrations/20261124000000_compliance_money_docs.sql` (Drizzle: `drizzle/0016_compliance_money_docs.sql`).

## Courier and payment provider seam

Merchant does not embed a courier or payment SDK. Instead it accepts signed events from whichever provider you use and exposes one signed outbound handoff:

- Inbound `POST /api/integration/courier` accepts `assigned`, `picked_up`, `out_for_delivery`, `delivered` and `failed`. Outbound delivery events only apply to delivery orders; `out_for_delivery` and `delivered` advance the order status through the normal event history. Payment webhooks accept `authorized`, `paid`, `failed` and `refunded` and update `paymentStatus` and a reference; they never change an order's money amount.
- Each event body carries `eventId`, `businessId`, either `orderId` or `orderCode`, `type`, `occurredAt` and optional `trackingId`/`reference`. The signature header is `x-savour-signature: t=<unix seconds>,v1=<hex HMAC-SHA256>` over `<t>.<raw JSON body>`, using `COURIER_WEBHOOK_SECRET` or `PAYMENT_WEBHOOK_SECRET` (32+ characters). Signatures older than five minutes are rejected. Replayed event ids return `{ outcome: "duplicate" }` without changing state; events older than the last provider update return `{ outcome: "ignored" }`.
- All accepted and ignored events are durably recorded in `provider_events`, and every decision is audit logged. The order DTO exposes `courierStatus`, `courierTrackingId`, `paymentReference` and provider timestamps so the UI can show authoritative provider state rather than guessing from a manual button.
- When a merchant advances a delivery order to `out_for_delivery`, Merchant posts a signed `delivery.dispatch` payload to `COURIER_DISPATCH_URL` (with `COURIER_DISPATCH_SECRET`) containing the order id/number, customer, address and item names/quantities. The status change is committed first; an unreachable or rejecting provider is audited and returned in the response as `dispatch.sent: false` instead of rolling back the handoff. With no dispatch URL configured, the existing manual rider flow remains unchanged. Non-loopback dispatch URLs must use HTTPS in production; loopback HTTP is allowed for local validation.
- Paired Marketplace listings are excluded from this seam: Marketplace owns their order state, so provider events for those businesses are rejected with 409. Configure provider webhooks on Marketplace instead.

## Operational notes and limitations

- The customer marketplace bundled in Merchant remains a separate first-party surface, not the external Marketplace. Checkout for a paired Marketplace business is refused so it does not receive duplicate orders; its menu and orders are read from Marketplace instead.
- Accounts currently support email/password only. Email verification and password reset are implemented: registration issues a hashed, expiring, single-use verification link, `forgot-password` answers identically whether or not an address exists, and a reset revokes every session and issues a fresh one to the current browser. Verification state is shown in the workspace, and merchant APIs reject unverified accounts only when `REQUIRE_EMAIL_VERIFICATION=true` (default off); `/api/auth` reads, logout, password change and resend-verification remain available so a gated account can recover. Keep the gate off until delivery is configured, otherwise new accounts cannot complete verification. Role-based staff access is implemented (see above); MFA and a production identity-provider integration are not implemented. Sessions use a 30-day idle timeout that slides forward on use (refreshed at most once a day) with a 90-day absolute lifetime: a fresh sign-in replaces any token already in that browser, expired rows are pruned and each account keeps at most 10 live sessions (oldest are dropped). "Sign out of all devices" revokes every session for the account. Signed-in users can change their password after confirming the current one; the change revokes every existing session and issues a fresh one to that browser. Harden CSRF and monitoring for the deployment; audit retention is covered below.
- Set `RESEND_API_KEY` and a verified `EMAIL_FROM` to send account emails through Resend; `APP_ORIGIN` supplies the canonical link origin. Without those values the adapter logs one warning and skips delivery, but the tokens are still created so the flows can be tested against the database. Verification links last 24 hours and reset links 30 minutes; both are stored only as SHA-256 hashes, redeemed atomically at most once, and issuing a new link invalidates earlier ones for the same purpose. No address, token or new password reaches logs or audit detail. Live delivery still has to be exercised with real credentials; only then enable `REQUIRE_EMAIL_VERIFICATION`.
- Rate limiting uses Upstash Redis (or Vercel KV) when `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN` (or `KV_REST_API_URL`/`KV_REST_API_TOKEN`) are configured, and otherwise falls back to a per-instance in-memory limiter with a startup warning. Client identity comes only from a proxy-managed header: set `TRUSTED_PROXY_IP_HEADER` to the header your proxy overwrites, Vercel's `x-vercel-forwarded-for` is used automatically, and without either all production clients share one bucket rather than trusting spoofable `x-forwarded-for`. Set `APP_ORIGIN` to the canonical deployment origin so mutating requests are checked against it instead of the `Host` header.
- API JSON bodies are size-limited per route (see `BODY_LIMITS` in `src/lib/server.ts`) and rejected with `415` for non-JSON content types, `413` when oversized, and `400` for malformed or empty bodies. Increase a limit only alongside the payload that needs it.
- Page responses carry a per-request nonce CSP generated in `src/proxy.ts`: `script-src 'self' 'nonce-…' 'strict-dynamic'` with no `'unsafe-inline'` (dev only adds `'unsafe-eval'`), and Next.js automatically nonces its framework scripts and inline bootstraps. `style-src` uses the nonce for style elements but keeps `style-src-attr 'unsafe-inline'` because React's inline style attributes in the error and loading boundaries cannot carry nonces. All page routes render dynamically via `connection()` in the root layout so every request gets a fresh nonce; API routes, static assets and prefetches skip the proxy. Google Fonts and merchant-supplied HTTPS menu images remain allowed; worker, object, frame, base-uri and form targets are locked down. HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy` and `Cross-Origin-Opener-Policy` stay in `next.config.ts`.
- Route-level `error.tsx`, `loading.tsx` and `not-found.tsx` boundaries provide Try again, skeleton and 404 fallbacks instead of Next's default screens. `global-error.tsx` handles failures in the root layout and owns its own document markup and styles because it replaces that layout. The integration suite checks the 404 response.
- Observability uses one JSON object per line (`src/lib/telemetry.ts`): `ts`, `level`, `event` plus explicit safe fields. Unexpected API errors include a request id, method, path and hashes of the client IP and user agent; stack traces are emitted only in development; error messages are stripped of email addresses and long opaque identifiers, so logs carry no bodies, headers or secrets. Client error boundaries emit the same shape. Rate-limit fallback warnings are a single structured event per process.
- Security-significant decisions are appended to the `audit_logs` table by `recordAudit()` in `src/lib/server.ts`: sign-in success/failure, registration, logout/sign-out-all, password changes, admin approval grants and rejections, staff invitations/role changes/removals and permission denials, provider webhook acceptance/rejection and courier dispatch attempts, Marketplace pairing/unpairing and rate-limit trips. Email, IP and user agent are stored only as SHA-256 hashes; detail values are scalar, truncated and redacted when the key looks secret. The table has no application update/delete path and no foreign keys, so records survive account deletion. Audit write failures are logged rather than returned to the caller. Retention defaults to 90 days: `npm run audit:prune` is a dry run that reports how many rows are eligible, and `npm run audit:prune -- --apply` deletes them in bounded batches with `SKIP LOCKED`; set `AUDIT_RETENTION_DAYS` to change the window. `.github/workflows/audit-prune.yml` applies it daily at 03:17 UTC from a trusted runner (manual runs are dry-run by default); it needs a `PROD_DATABASE_URL` repository secret and an optional `AUDIT_RETENTION_DAYS` repository variable — the app itself has no delete path. Read access is granted only to the `audit_reader` group role (NOLOGIN, no write grants), which has a scoped RLS SELECT policy; grant that role to a dedicated operations login outside migrations. No browser or Data API role has table access.
- Notifications use sensible foreground polling and optional browser notifications/sound. They are not push notifications and are not reliable with the page closed or the device offline. Browser permission and sound policies apply. Offline changes are not queued: the UI reports failures and reloads authoritative state on reconnection.
- Only cash/unpaid customer checkout is supported in the bundled first-party marketplace; there is no payment gateway, courier integration, delivery-completion webhook or refund processor. For paired businesses, Marketplace owns customer payments, merchant bank/UPI details and the real provider payout; Merchant only validates and mirrors the resulting net settlement records. Delivery destinations are collected and delivery orders can be advanced manually from ready → out for delivery → completed. That manual path is a simulation, not proof of an authoritative courier handoff; the signed provider webhook seam above is how a real courier can make delivery completion authoritative. Net proceeds are shown only from confirmed Marketplace records, never estimated from local orders.
- Business hours are a simple daily schedule in India Standard Time, now overlaid by temporary closures (automatic expiry) and planned leave days in Asia/Kolkata. Map location, per-day recurring hours, menu-image upload storage and add-ons/customisations still require integration work; compliance documents use their own private bucket as described above. Staff access uses the local role model above; delegating staff management or pairing to Marketplace would need an integration. Each outlet is a separate Marketplace listing: there is no single customer-facing listing with a branch selector, no shared brand/organisation record, and no combined revenue/order view across outlets — use the switcher to work one outlet at a time. Menu images accept HTTPS URLs; no file-upload service is configured.
- Public marketplace orders have no customer identity system; a high-entropy order token is kept in browser storage for status lookup, retry and feedback submission. A production customer authentication, privacy and order-recovery design is required. Reviews are immutable and scoped to that token; the merchant reply is public to anyone holding it, so do not include personal details in a reply. Offer codes are public by design: the customer-side discount preview only helps customers choose a code, and the authoritative discount is recalculated and persisted by the server when the order is placed.
- Approval requires the server hook above or a trusted administrative process. There is no automatic approval or invented verification result. Currency is INR in paise.
- The initial migration creates new tables only because no pre-existing business/order tables were present; the second adds the delivery-address field; the third (`20261028000000_marketplace_bridge.sql`) replaces the earlier OAuth link columns with `business_marketplace_links`; the fourth adds the unique Marketplace restaurant index declared in the schema; the fifth adds the append-only security audit table; the sixth adds email verification state and the hashed account-token table; the seventh adds authoritative settlement fields, sync timestamps and duplicate-proof indexes; the eighth creates the restricted `audit_reader` role and its SELECT policy; the ninth adds immutable customer-review and merchant-reply columns to `orders`; the tenth creates the `offers` table and adds `offer_id`, `offer_code` and `discount` to `orders`; the eleventh creates the `staff_members` table with its unique business/user membership index; the twelfth adds provider-sourced courier/payment columns to `orders` and the deduplicated `provider_events` log; the thirteenth adds temporary-closure columns to `businesses`; the fourteenth adds item stock and modifier groups; the fifteenth allows one owner to run multiple outlets, adds the session's active outlet and backfills existing sessions; the sixteenth adds per-outlet compliance records, encrypted document metadata, agreement acceptances and mirrored/pro forma tax invoices. Review them against any target database before deployment.
- Production dependencies have no known high or critical advisories: `npm audit --omit=dev --audit-level=high` is clean and enforced in CI. The minimatch (ESLint) chain and the high-severity PostCSS advisory were fixed by refreshing the lockfile and bumping the dev-only `postcss` pin. Four moderate advisories remain in dev-only tooling: `drizzle-kit`'s `@esbuild-kit/esm-loader` pins `esbuild@~0.18.20` (a dev-server request exposure). npm's suggested fix is a breaking downgrade to `drizzle-kit@0.18.1`, and an override would jump esbuild across incompatible 0.x APIs, so neither is applied for a local-only migration tool. Re-evaluate when drizzle-kit ships a fix that keeps the current migration API.

## Validation

Run `npm run typecheck`, `npm run lint` and `npm run build`.

`npm run test:settlements` validates the authoritative settlement payload contract without a database, `npm run test:compliance` checks compliance validation, agreement hashing and Marketplace payout/invoice parsers, `npm run test:provider-events` checks provider payload validation and raw-body HMAC signatures, and `npm run test:urls` checks that loopback HTTP is accepted for local production validation while real endpoints still require HTTPS. The API integration smoke test in `scripts/integration-test.mjs` covers security headers and nonce freshness, the default-off verification flag, order concurrency, API ingress limits, session policy, password change, customer feedback and replies, offer creation/redemption/limits, staff invitations/role changes/removals and server-enforced permission checks, multi-outlet ownership and per-outlet staff roles, session-scoped outlet switching and cross-outlet access denial, signed courier/payment webhooks (when secrets are configured), the stored settlement mirror, compliance permissions/advisories, agreement acceptance, and pro forma invoice + labelled PDF generation. Document upload/download needs a configured private bucket and is not exercised by that suite. It needs a running server and a **disposable local database**; the script refuses any `DATABASE_URL` whose host is not `127.0.0.1`, `localhost` or `::1`, and it deletes the records it creates. `npm run test:verification-gate` checks the opt-in gate against a separate local server started with `REQUIRE_EMAIL_VERIFICATION=true`; it is not part of the default suite because it needs that different server configuration.

```bash
# 1. Point DATABASE_URL at an empty local PostgreSQL database, then apply the schema in order.
for file in drizzle/*.sql; do psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f "$file"; done

# 2. Build and start the app with DATABASE_URL set (npm start runs a production build).
npm run build
npm start

# 3. In another terminal, run the suite against it.
npm test
```

Never run `npm test` against production: it registers accounts, places orders and edits sessions directly.

Continuous integration runs on every push to `main` and every pull request (`.github/workflows/ci.yml`): route type generation, typecheck, lint, production build, the integration suite against a disposable PostgreSQL 17 service container, and a production-only dependency audit. No CI secrets are required; the workflow uses CI-only placeholder values.

The retention workflow (`.github/workflows/audit-prune.yml`) runs daily at 03:17 UTC and can also be dispatched manually. Its dry-run step always runs; the apply step runs on the schedule or when the manual `apply` input is selected. Configure `PROD_DATABASE_URL` as a repository secret pointing at the production database, and optionally set the `AUDIT_RETENTION_DAYS` repository variable (default 90). The workflow uses `SKIP LOCKED`, a 10-minute timeout and a non-cancelling concurrency group so runs cannot overlap. It only starts once the workflow is on the default branch in GitHub.
